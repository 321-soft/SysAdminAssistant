# Отображение резервного копирования 0.38.0

Главная строка теперь отвечает на вопрос о текущем ожидаемом запуске: «Нет отчёта», «Ожидается», «Результат не распознан», «Успешно», ошибка или предупреждение. Старый успех больше не выводится главным результатом при пропущенном отчёте.

История показана отдельно: «Последний отчёт: ДД.ММ.ГГГГ ЧЧ:ММ · Успешно». Эта дата — время результата, которое уже используется моделью отчётов; повторного смещения часового пояса нет. Длинная подпись переносится, чтобы дата не скрывалась за обрезкой.

В списке «Резервное копирование» впереди находится текущий статус и его индикатор; последний результат, дата и исторический индикатор явно отделены. Старый зелёный результат остаётся историческим, а не подтверждает новый запуск. При ожидании/неопределённости старый зелёный не превращает текущую строку в подтверждённо зелёную. Критические/предупреждающие последние результаты сохраняют приоритет цвета; выключенный контроль серый.

«Нет отчёта» означает отсутствие подтверждения запуска, а не доказанный сбой самого бэкапа. При поломке почты проверь диагностику IMAP и поступление писем; после получения свежего подходящего успешного отчёта строка снова станет зелёной. Правила расписаний, допуски, анализ почты и автоматическое закрытие проблем не менялись.

Обнови клиент и сервер полным опубликованным комплектом. Если клиент уже открыт, получи новый снимок кнопкой «Обновить». Переустановка агентов и удаление БД не нужны.

# Изменения поведения 0.37.0

## Обучение счетов
Настройки → Счета из почты → Поставщики и обучение → Добавить. Диалог имеет собственную блокировку действий, независимую от открывшего его окна настроек. Нужны права настройки и записи счетов; серверная проверка ролей сохранена.

## Одна активная проблема и история повторений
Распознанные ошибки бэкапов группируются по устройству, заданию, конкретному запуску и сигнатуре причины. Время в тексте нормализуется; для известной ошибки слишком длинного пути меняющиеся ежедневные имена файлов не создают отдельные проблемы. Другие неизвестные причины сравниваются консервативно, без объединения всех ошибок по одному общему слову.

В активном списке показываются число повторов, первое и последнее время. Закрытые записи доступны через «Показывать закрытые события (история)»; исходные письма и результаты каждого запуска сохранены. Закрытие сгруппированной строки закрывает все входящие в неё события в одной операции. В карточке устройства также показывается одна сгруппированная проблема.

После более позднего распознанного успешного отчёта того же устройства и запуска старые ошибки закрываются автоматически. Отчёт другого запуска/устройства, будущий/старый успех, предупреждение вместе с успехом и неизвестный результат не подтверждают восстановление. Исправление настройки само по себе не доказывает успешный бэкап — нужен отчёт. Пропущенные запуски контролируются отдельно и не становятся успешными задним числом.

Сверка запускается сервером; клиент и закреп читают одни и те же закрытые события. Уже открытое окно клиента обновляется через получение нового снимка кнопкой «Обновить», без постоянной перезагрузки форм.

## Telegram
Обычные сообщения содержат название и адрес устройства, если событие связано с устройством, а также задание для бэкапа. События серверной сети/общей почты без устройства остаются общими.

Для новых сообщений сохраняется Telegram message_id по конкретному боту и чату. Сообщение о закрытии/восстановлении отправляется ответом на исходную проблему, с зелёным индикатором. Корреляция сохраняется после перезапуска сервера; новый цикл сбоя получает новую исходную запись. При смене бота/чата чужие ID не используются.

Сообщения старых версий не имеют сохранённого ID: восстановление придёт отдельно. Если исходное сообщение удалено, включён allow_sending_without_reply; при явном отказе Telegram из-за отсутствующего оригинала выполняется отдельная отправка. Ошибки доступа и ограничения Telegram не обходятся. Категории, уровни важности и галочка восстановления продолжают действовать.

Одинаковая продолжающаяся проблема бэкапа не отправляется каждый день заново; счётчик растёт в клиенте и закрепе. Изменение причины или повышение важности может дать новое уведомление. Старые дубликаты в ожидающей очереди объединяются без удаления истории. Очередь и квитанции защищены каталогом данных сервера; пароли и токен в квитанции не записываются. При аварии между успешной отправкой Telegram и сохранением квитанции возможен повтор — внешняя API не предоставляет транзакцию вместе с локальной БД.

Документация Telegram Bot API: https://core.telegram.org/bots/api#replyparameters

# Важно для версии 0.36.0

Windows-агент с длинным именем Hyper-V интерфейса мог оставаться Running, но не отправлять ни одного отчёта из-за локальной валидации. Исправление — в Windows-агенте 0.36.0; сервер и клиент сами по себе старый процесс не исправляют. Обнови сервер из новой публикации вместе с полным AgentTemplate; дождись штатного автоматического обновления агента. Если автообновление не произошло, используй штатный установщик с сохранением существующей регистрации, не удаляя ProgramData. Состояние обновления не заменяет проверку свежего принятого отчёта в карточке устройства.

Диагностика: C:\ProgramData\SysAdminAssistantAgent\status.json содержит этап, код и категорию ошибки. Длинное имя адаптера представлено читаемым префиксом и стабильным хэш-суффиксом; короткие имена не меняются. Если проблема осталась, пришли только status.json, не bootstrap.json или identity.bin.

# Windows Agent 0.12.2

Агент только наблюдает: uptime, CPU, RAM, локальные диски, состояния выбранных служб, журналы Windows и локальный кэш Windows Update. Входящих портов и команд управления нет. Служба LocalService с отдельным SID; конкретные службы, пороги и правила журналов задаются в карточке устройства. См. WINDOWS_EVENTS.md.

## Установка и обновление

Устройство → Агент → Создать установщик. Укажи HTTPS IP сервера и разрешённые подсети назначения, выбери место ZIP. Пакет создаётся из готового AgentTemplate; SDK на мониторируемой машине не требуется. Runtime берётся из локального проверенного кэша / Prerequisites; загрузка при отсутствии требует согласия.

Распакуй ZIP целиком, запусти INSTALL_AGENT.cmd, сверь сервер и издателя. После регистрации сверь открытый ключ с ProgramData/SysAdminAssistantAgent/status.json и подтверди агента в карточке. Не передавай identity.bin и bootstrap.json: там секреты.

Для уже установленного агента создавай «Пакет обновления агента» именно из его карточки. Обновление сохраняет ключ и привязку. В 0.12.2 один раз установи его локально с флажком автоматического обновления; далее обслуживание получает новые подписанные версии с того же сервера. Подробности — AGENT_AUTO_UPDATE.md. Ошибка установки показывает этап, HRESULT и журнал; проверка — ../UPDATES.md.

## Сертификаты

Сертификат регистрации автоматически продлевается заранее при связи с сервером. Если агент отсутствовал до истечения, в карточке → Сертификаты разреши восстановление на 24 часа, сверив прежний ключ. Новая регистрация и переустановка не нужны.

Будущий публичный DER .cer HTTPS-сертификата заранее добавь на сервере и дождись получения подписанного доверия агентами. После перехода можно оставить доверенным только текущий сертификат. Если связь уже потеряна, экспортируй подписанное доверие из Assistant и в локальном установщике выбери «Импорт доверия HTTPS». Принимается только подпись прежнего центра регистрации, без отката версии. Центр регистрации и его резервную копию нужно сохранять; потеря ключа не восстанавливается файлом доверия.

## Проверка

Служба SysAdminAssistantAgent должна работать под LocalService. Фиксированная задача SysAdminAssistantAgentUpdateRead читает локальный кэш обновлений ОС под SYSTEM; ничего не скачивает и не устанавливает. При включённом автообновлении отдельная задача SysAdminAssistantAgentAutoUpdate обслуживает только сам агент. Скрипт verification/VerifyAgentWindows.ps1 проверяет установленную конфигурацию.

Сборка и переносимые тесты выполнены на Linux. Windows GUI, UAC, SCM, DPAPI, Task Scheduler и живое обновление с откатом здесь не выполнялись. Сначала проверь одну тестовую Windows-машину.

# Автоматическое обновление агента

## Включение один раз

Обнови сервер и клиент до 0.12.2 одной публикацией PUBLISH.bat. Создай «Пакет обновления агента» в карточке устройства. На машине агента распакуй его целиком, запусти INSTALL_AGENT.cmd, сверь издателя и оставь флажок «Автоматически обновлять агент с этого сервера». Установка сохраняет identity.bin, сертификат, настройки, ID устройства и привязку. Агенты прежних версий сами установить этот механизм не могут.

Проверка выполняется каждые 15 минут и через 2 минуты после загрузки Windows. Для следующих версий достаточно обновить сервер через SETUP_SERVER.cmd целой папкой ServerSetup. В неё PUBLISH.bat включает AgentTemplate/Agent и AgentTemplate/Setup. SDK на контролируемой машине не нужен. Для .NET 10 x64 используются уже установленные runtime; смена основной ветки .NET требует отдельного перехода.

## Что выполняется с повышенными правами

Сама служба SysAdminAssistantAgent остаётся LocalService и только мониторит. Отдельная фиксированная задача планировщика SysAdminAssistantAgentAutoUpdate запускается под SYSTEM. Она обслуживает только файлы и службу собственного агента. Нет произвольных команд, установки обновлений Windows/RouterOS или входящих портов.

Конфигурация задачи и bootstrap-копия находятся в Program Files/SysAdmin Assistant Agent/Maintenance. Запись разрешена администраторам и SYSTEM; служба агента имеет чтение. Два каталога A/B позволяют обновлять установщик, не заменяя запущенный файл. Параллельное локальное / автоматическое обслуживание блокируется. Не выдавай обычным пользователям и службе право записи в Program Files.

## Проверки перед заменой

- Только исходный HTTPS IP и разрешённые при установке подсети; без перенаправлений, прокси и внешних загрузок сертификатов.
- Запрос подписан ключом зарегистрированного, подтверждённого и неотозванного агента. Отдельный протокол не меняет счётчик отчётов.
- Выпуск подписан прежним центром регистрации сервера; связан с ID агента, случайным запросом и коротким сроком действия. Версия ниже установленной не принимается.
- Состав файлов ограничен: только собственные exe/dll и runtime JSON в фиксированных каталогах, без путей и скриптов. Каждый файл проверяется по размеру и SHA-256 до остановки службы.
- При сбое запуска новой службы выполняется попытка отката прежних файлов. Ключ и регистрация не меняются. Ошибки обслуживания отражаются в карточке устройства после следующего отчёта.

Сервер, его центр регистрации и публикация являются доверенной стороной: их компрометация означает возможность распространить вредоносную версию. Защищай администраторские права и резервные копии сервера. Никакой механизм не гарантирует полного отсутствия уязвимостей.

## HTTPS и отключение

Ротация доверия HTTPS используется прежняя: заранее добавь будущий сертификат на сервере и дождись получения доверия агентами. Если связь уже потеряна, импортируй подписанный файл доверия локально. Переустановка не нужна; новый центр регистрации или неизвестный сертификат автоматически не принимаются.

Чтобы отключить автоматическую установку, повторно запусти локальный пакет своего агента и убери флажок. Задача обслуживания удалится; мониторинг продолжится. Удаление локального агента удаляет обе его задачи. Нативный сценарий Windows необходимо проверить на одной машине перед массовым развёртыванием.

# Подробности проблем и рекомендации

Версия 0.31.2 добавляет пояснения в карточки проблем, окна агентов/журналов и новые уведомления Telegram. Подробности уже существующих проблем формируются при открытии карточки из сохранённых данных. Ранее отправленные сообщения Telegram не редактируются и не рассылаются повторно ради новых пояснений. Закреп остаётся компактной сводкой.

Для CPU, RAM, дисков, интерфейсов и служб показаны реальные значения из отчёта, порог, время и рекомендации. Для отсутствующей метрики не придумывается нулевое значение. Для журналов показаны правило, источник, ID, повторы, условия закрытия и исходные записи, если они сохранились. Источники и сведения, которых нет в отчёте, не восстанавливаются догадкой.

Все стандартные события Windows/Linux, стандартные правила журналов MikroTik, контроль API, чтения журналов и нестабильности интерфейсов имеют пояснения. Для пользовательских/неизвестных правил даётся общий порядок проверки и исходное сообщение. Существующие объяснения отчётов резервного копирования и аудита конфигурации сохранены.

Для /boot и /boot/efi показаны объём, свободное место и сработавшие условия. Если абсолютный порог не меньше всего раздела, сообщение указывает на неподходящую настройку. Порог ГиБ общий для устройства; его изменение затронет остальные тома. Само правило срабатывания в этой версии не менялось. Файлы ядра, загрузчика и другие данные автоматически не удаляются.

Рекомендации не являются автоматическим исправлением. Команды в сообщениях предназначены для просмотра. Изменения служб, файловых систем, firewall и пакетов следует выполнять только после проверки причины. В Telegram передаются факты и рекомендации без добавления полного сырого текста журнала; полный текст доступен в программе. Для проверок HTTP параметры URL и учётные данные не выводятся в пояснение.

Пояснения вычисляются сервером и клиентом по уже существующим отчётам. Для этой функции обнови сервер и клиент. Переустановка агентов не нужна; формат их подписанных отчётов не изменён.

Справочные материалы:
- systemctl: https://www.freedesktop.org/software/systemd/man/latest/systemctl.html
- journalctl: https://www.freedesktop.org/software/systemd/man/latest/journalctl.html
- Разбор неожиданных перезагрузок Windows: https://learn.microsoft.com/en-us/troubleshoot/windows-server/performance/troubleshoot-unexpected-reboots-system-event-logs

Рекомендации — ориентир для проверки, а не доказательство конкретной причины по одному событию.

В 0.32.0 Linux-данные расширены: дисковые пороги /boot больше не наследуют общий абсолютный минимум, inode и systemd контролируются отдельно. Рекомендации обновлены под фактические данные, детали — LINUX_UPDATE_0.32.md.

# Профили служб агента

Профили находятся в карточке устройства → Агент → Роли и службы → Роли сервера. Можно выбрать несколько. До сохранения виден список добавляемых и удаляемых служб; источник виден в таблице. Это настройка мониторинга, не установка/запуск/остановка служб.

| Роль | Основной контроль | Условные компоненты |
|---|---|---|
| AD DS | NTDS, Kdc, Netlogon, LanmanServer, RpcSs, SamSs, EventSystem, LanmanWorkstation, Dnscache, W32Time | DNS/ADWS если установлены и не Disabled; DFSR/NtFrs при Automatic или Running |
| DNS | DNS | не Dnscache |
| DHCP | DHCPServer | не клиентская Dhcp |
| SQL | MSSQLSERVER, MSSQL$INSTANCE из инвентаря | SQLSERVERAGENT/SQLAgent$INSTANCE и SQLBrowser при Automatic/Running |
| 1С | службы агентов сервера по системному/отображаемому имени | несколько установок; не процессы rmngr/rphost и не удалённая SQL |
| SMB | LanmanServer, RpcSs, SamSs | SrmSvc при Automatic/Running; DFS отдельно |
| DFS Namespace | Dfs, LanmanServer, RpcSs | только сервер пространства имён |
| DFS Replication | DFSR | только участник репликации |
| IIS | W3SVC, WAS | проверка сайтов отдельно |
| Hyper-V | vmms | только хост |
| RDS Session Host | TermService | SessionEnv/UmRdpService при Automatic/Running |
| AD CS CA | CertSvc | не штатно выключенный офлайн CA |

Фиксированная основная служба выбранной роли ожидается даже при отсутствии. Имена экземпляров SQL/1С берутся из отчёта агента; если не найдены, выдаётся предупреждение о необнаруженной основной службе. Disabled экземпляры при первом обнаружении не добавляются. Ранее обнаруженная служба после исчезновения сохраняется: её удаление не превращает аварию в зелёный статус. При недоступности инвентаря старые правила не вычищаются.

Важность: W32Time/ADWS/SQLBrowser — Warning; остальные — Critical. Задержка профиля 2 минуты; ожидание после загрузки — текущая настройка устройства. Значения можно переопределить вручную. Один профиль не должен навязывать универсальное Running всем вспомогательным службам: VSS, ручные/триггерные компоненты, Spooler и службы обновления не добавляются просто по наличию. На кластерах/пассивных узлах требуются ручные ожидания или исключения.

Удаление роли убирает только её источник. При нескольких владельцах строка остаётся. Ручная запись побеждает профиль. Изменение строки делает её ручной; приостановка создаёт ручное disabled-правило; удаление убирает строку и сохраняет исключение отдельно. Старые JSON-записи без происхождения неотличимы от ручных, поэтому сохраняются. Они явно помечены «Ручная / прежняя настройка» и могут быть удалены вручную. Новые автоматически обнаруженные записи помечаются источником, включая базовые Windows. После первого сохранения ролей автоматическое угадывание AD больше не возвращает снятую роль.

Лимит — 64 сохранённых правила. Если экземпляров слишком много, отчёт агента не отклоняется: сохраняются ручные и ранее отслеживаемые записи, об остальных выдаётся предупреждение. Выбрать нужные экземпляры вручную. Политика хранится на сервере, пересобирается при сохранении и поступлении отчёта; версия меняется только при изменениях. Агент получает плоский список, поэтому существующий агент уже умеет выполнять проверки; новые поля происхождения ему не нужны.

# Единый Setup.exe для агента

В карточке устройства создаётся один EXE. Он содержит сжатый пакет с готовым агентом, мастером установки, серверной регистрацией и Microsoft .NET Desktop Runtime из локального хранилища. При отсутствии Runtime клиент спросит о загрузке в хранилище; последующие пакеты используют его повторно. Установщик Runtime уже сжат Microsoft, поэтому именно он определяет большую часть размера EXE. Конкретный размер показывается Windows после сохранения; обещания нескольких мегабайт нет.

При создании нет компиляции и запуска SDK. Маленькая оболочка собирается только при PUBLISH.bat системным компилятором .NET Framework Windows, код включён в packaging. .NET Framework 4.6.2 входит в Windows Server 2016; на более новых Windows используется совместимая системная версия. Это оболочка для установки, агент работает на .NET 10.

Запуск Setup.exe требует UAC. Каталог распаковки имеет случайное имя в ProgramData и разрешён только администраторам и SYSTEM. Перед распаковкой проверяется SHA-256 содержимого, все пути, дубликаты имён и пределы размеров; пути вне каталога, ADS и повреждённые данные отклоняются. После завершения мастера каталог удаляется. Runtime проверяется по SHA-512 и подписи Microsoft, существующий подходящий Runtime повторно не устанавливается. При требуемой перезагрузке показывается сообщение без принудительного рестарта.

SHA-256 внешнего контейнера защищает от случайной порчи, а не доказывает издателя. Внутренняя регистрация подписывается сервером и проверяется мастером, хеши агента сверяются с ней. Персональный EXE не имеет Authenticode-подписи Windows: Windows может показать неизвестного издателя. Не путай подпись регистрации с подписью EXE. Для публично доверенного подписанного EXE нужна отдельная подпись готового персонального файла сертификатом подписи кода; закрытый ключ не распространяется клиентам. Опциональная подпись опубликованных файлов агента сохраняется, оболочка-шаблон исключена, поскольку добавление персонального содержимого изменяет итоговый EXE.

Пакет регистрации остаётся временным секретом одного устройства. Не публикуй его; срок действия 24 часа. Подтверждение ключа агента на сервере обязательно.

## Мастер удаления

Запусти UNINSTALL_SERVER.cmd от имени администратора **из отдельной распакованной папки**. .NET SDK для этого мастера не нужен: он использует Windows PowerShell и Windows Forms.
REMOVE_SYSADMIN_SERVER_ALL.bat теперь открывает тот же мастер, а не выполняет удаление всего одним общим подтверждением.
ExecutionPolicy Bypass применяется только к текущему запуску PowerShell; политика системы не меняется.

Поиск использует зарегистрированную службу, стандартные папки ProgramData/LocalAppData и Program Files версий 0.3–0.6. Нестандартную папку с server.json и settings.json можно добавить вручную.
Для каждого сохранённого SQL-подключения показываются SQL-сервер, база, папка настроек и результат проверки.
Для SQLite показывается полный путь; дополнительные SQLite-файлы в корне папки установки выводятся отдельными строками.
Список не является поиском всех SQL-баз на всех серверах: базы без конфигурации и чужие профили Windows автоматически не обходятся.

Изначально все флажки удаления сняты. Для каждой выбранной базы запрашивается отдельное подтверждение, затем итоговый список.
SQL-база удаляется только при успешном подключении и наличии таблиц SysAdmin Assistant. Системные базы запрещены.
Если секрет подключения не расшифровывается или SQL недоступен, база остаётся непроверенной, удалить её через мастер нельзя.
Если несколько конфигураций указывают на одну базу, необходимо выбрать их все, иначе удаление блокируется.

Отдельно можно выбрать удаление папок программы/данных и служебных учётных записей выбранных установок.
Папка с невыбранной базой, дополнительным невыбранным файлом базы или резервной копией не удаляется.
Учётка удаляется только с маркером принадлежности программе и при отсутствии использующих её служб; учётки сохранённых установок остаются.
.NET runtime, клиент и невыбранные базы сохраняются.

После последнего подтверждения мастер останавливает службу. Сначала удаляются выбранные базы, затем регистрация службы, правило firewall, выбранные учётки и папки.
При ошибке процесс прекращается. Удаление НЕ является общей транзакцией: ранее удалённые базы автоматически не восстанавливаются. Мастер не создаёт резервную копию. Если данные нужны, сохрани их заранее средствами SQLite/SQL Server и скопируй настройки.
При частичной ошибке повторно открой мастер. Если Windows удерживает удалённую службу, закрой services.msc либо перезагрузи сервер.

## Новая установка

Запусти SETUP_SERVER.cmd из подготовленной папки ServerSetup. Укажи отдельные пустые папки и новую базу.
Для SQL установщик создаёт базу с указанным именем. Существующая база не перезаписывается.
Пароль администратора приложения — 9–256 символов. Служебная Windows-учётка создаётся автоматически со случайным паролем; пароль твоей Windows-учётки не нужен.
После установки выдай пользователям права и заново настрой интеграции. Автоматического переноса старых данных в этом выпуске нет.

# Web, SSH и RDP · 0.34.0 TEST

Обнови сервер и клиент одной версии. В карточке устройства нажми «Настроить подключения»:

- Web / WebFig: полный URL, например https://192.168.20.1:8443/webfig/. Он не связан с портом RouterOS REST API. HTTP тоже допустим при явной настройке.
- SSH: IP/DNS без URL и порта, порт (обычно 22), необязательный логин.
- RDP: IP/DNS, порт (обычно 3389), необязательный логин, в том числе DOMAIN\user.

Поставь галочки нужных способов и сохрани. Ненастроенные кнопки неактивны. У MikroTik кнопки находятся в карточке «Состояние и события», на верхней панели; Web открывает WebFig в браузере по умолчанию. Параметры меняют пользователи с правом изменения соответствующего раздела «Устройства» или «Коммутаторы / сеть».

Подключения запускаются **на компьютере клиента Assistant**. Сервер и агент не являются прокси и не выполняют SSH/RDP-команды. Web использует браузер по умолчанию. SSH запускает штатный Windows OpenSSH из системного каталога; если клиент OpenSSH отсутствует, появится понятное сообщение. Устанавливать его нужно на рабочем компьютере, не на сервере мониторинга. RDP открывает временный .rdp-файл через приложение, назначенное для этого расширения (обычно mstsc).

Пароли здесь не хранятся: вводи их во внешнем клиенте или используй прежний менеджер паролей. В URL нельзя помещать логин/пароль вида user:password@host; не сохраняй в URL секретные токены. URL, адреса и имена пользователей — обычные метаданные устройства, доступные читателям его раздела. В SSH не передаётся командная строка shell; аргументы формируются отдельно. Проверка сертификатов и ключей хостов не отключается.

RDP-файл содержит только адрес, порт, необязательное имя пользователя и запрос учётных данных. Временные файлы хранятся в LocalAppData\SysAdminAssistant\RdpConnections; файлы старше недели удаляются при следующем запуске RDP. Секретов в них нет. Настройки постоянных подключений хранятся в БД с устройством и сохраняются при переносе БД. Excel-обновление существующего устройства не сбрасывает их; отдельные столбцы подключений в Excel не добавлялись.

Сборка через PUBLISH.bat. Сделай обычную резервную копию перед штатным обновлением сервера. В SQLite/SQL Server добавляется поле ConnectionsJson с пустым значением для прежних устройств; старые данные не удаляются. Обновление агента для этих кнопок не требуется. Исправление systemd из 0.33.1 и связь паролей с сервисами сохранены.

# Excel: устройства, сотрудники, пароли

В каждом списке есть «Скачать шаблон», «Экспорт Excel», «Импорт Excel». Сотрудники находятся в Инвентаризация → Сотрудники. Все файлы — XLSX, Excel на компьютере не обязателен. Старый XLS, CSV и XLSM не принимаются. Шаблоны встроены в приложение, загрузка из интернета не нужна.

1. Скачайте шаблон нужного раздела через «Сохранить как».
2. Заполните лист **Данные**, начиная со второй строки. Не переименовывайте лист и заголовки. Инструкция находится на втором листе. Можно добавлять строки под таблицей.
3. У новых записей ID и Версия пустые. Обязательны Имя / ФИО / Название. Активно и Работает: Да или Нет; пусто означает Да. Табельные номера уникальны, сохраняют ведущие нули, нормализуются как при ручном вводе: пробелы по краям убираются, буквы — в верхний регистр.
4. Нажмите «Импорт Excel», выберите файл и проверьте предпросмотр. При любой ошибке кнопка импорта недоступна; исправьте файл и откройте заново. После подтверждения сервер ещё раз проверит актуальные версии и сохранит все строки одной транзакцией. Ошибка означает, что ни одна строка не сохранена.
5. Для правки существующих записей сначала выгрузите их через «Экспорт Excel», сохраните ID и Версия и включите «Обновлять существующие». Сопоставления по похожему имени нет. Изменённые другим пользователем записи нельзя затереть старым файлом. Чтобы использовать строку как новую запись, очистите одновременно ID и Версия. Повторный импорт строк без ID создаёт новые записи.

Импорт ничего не удаляет. Существующие ссылки устройства, агента, имущества и владельца пароля сохраняются. Столбец Устройство ID в паролях — ID из выгрузки устройств; пусто снимает привязку. Для новой привязки нужно право чтения соответствующего устройства. Нельзя снять Работает у сотрудника с выданным имуществом. Устройства в этой выгрузке — обычный раздел Устройства; MikroTik и коммутаторы остаются в Коммутаторы / сеть.

Устройства: ID, Версия, Имя, Тип, Адрес, Площадка, Роль, Активно. Состояния мониторинга, расписания, учётные данные API и настройки агента не импортируются и не перезаписываются. Сотрудники: ID, Версия, ФИО, Табельный номер, Отдел, Должность, Контакт, Работает. Пароли: ID, Версия, Название, Логин, Пароль, Примечание, Устройство ID. Пустой Пароль при импорте означает именно пустой пароль, а не сохранение прежнего.

## Пароли

Чтение, экспорт и импорт требуют разблокировки текущим паролем учётной записи. Новые записи принадлежат импортирующему пользователю; существующий владелец не меняется. Действуют обычные права раздела и видимость записей. Предпросмотр не показывает логин, пароль или примечание. Сервер сразу шифрует импортируемые секреты штатным механизмом хранилища; XLSX на серверный диск не пишется, аудит содержит только действие. Приложение не обещает удаления всех копий секретов из управляемой памяти или операционной системы.

**Выгруженный Excel содержит открытые пароли**. Перед выгрузкой требуется отдельное подтверждение. Защищайте файл и место его хранения, не отправляйте через обычную почту. Не помещайте его в публичные папки или общий каталог. Сохранение использует временный файл рядом с выбранным итоговым файлом и затем переименование; при сбое выполняется очистка временного файла.

До 2000 записей, до 8 МБ XLSX, ограничен распакованный размер. Используйте значения, не формулы: формулы, макросы, внешние ссылки, повторяющиеся части ZIP и DTD отвергаются. Экспорт сохраняет текст буквальным: ведущий знак = не становится формулой. Скачанные шаблоны заранее форматируют ввод как текст для ведущих нулей и паролей; не преобразовывайте такие поля в числа средствами Excel.

## Обновление

Собрать PUBLISH.bat и обновить **сервер и клиент**. Переустанавливать агенты ради Excel не требуется. Схема БД не меняется. Интеграционные проверки HTTPS/DPAPI и GUI выполняются PUBLISH на Windows; результат Linux-проверок и ограничения — verification/AUDIT.md.

В каждой строке платежа с документами есть **PDF ↓**. В карточке платежа — «Счёт · реквизиты и документ» и скачивание. При нескольких документах/периодах предлагается выбор. PDF сохраняется без изменения исходных байтов через «Сохранить как». PNG/JPEG можно скачать оригиналом либо преобразовать в PDF с суффиксом converted. Файл не открывается автоматически. Исходный PDF хранится в БД сервера и доступен после удаления письма из IMAP. Письма без вложений имеют только текстовый просмотр, исходного PDF у них нет.

## Настройка с нуля

1. Соберите PUBLISH.bat, обновите сервер и клиент. Добавляются две таблицы архива InvoiceRecord / InvoiceAttachment; старые платежи и настройки не меняются. Для существующей SQL-базы нужны права на создание новых таблиц. Прежняя схема 7 сохраняется. Агентов ради счетов обновлять не нужно.
2. В настройках откройте «Почта для счетов». Лучше выделить папку или отдельный ящик: обработка отчётов и DMARC использует прежние настройки и независимый обработчик. Введите IMAP-адрес, TLS-порт, логин, пароль приложения, папку. Пароль хранится штатной защитой Windows на сервере, при следующем открытии не выдаётся клиенту.
3. Нажмите «Проверить подключение». Проверяются TLS, вход и чтение выбранной папки. Не требуется отдельно устанавливать Excel или SDK на сервере для распознавания.
4. По умолчанию загружаются только новые письма **после начальной проверки**. После сохранения включённых настроек начальная проверка запрашивается сразу; дождитесь в истории «Начальная отметка сохранена». Для старых документов выключите «Только новые» и задайте дату. При смене ящика/папки/начала загрузки создаётся новая отметка; для OnlyNew это новая начальная точка. После перерыва работа продолжается с сохранённого UID. Письма открываются в ReadOnly, флаг прочитанности не меняется.
5. Укажите точные адреса разрешённых отправителей. Для автоматического добавления включите проверку SPF/DKIM и настройте принимающую систему. Для Яндекса есть профиль; для другой почты укажите точные auth-id. Подтвердите очистку поддельных Authentication-Results только если ваш почтовый сервер действительно её выполняет. Один From без проверки подлинности не разрешает автоматическое создание платежа.
6. Первые документы появятся в очереди проверки. Откройте счёт: слева **текстовый предпросмотр**, справа поля. Проверьте поставщика, номер, сумму/валюту, дату счёта, срок и реквизиты. Срок не подменяется датой получения. Оригинал PDF скачивается отдельно; встроенного графического PDF-просмотрщика в этой версии нет. «Показать исходное письмо» выводит безопасный текст без внешних картинок.
7. Подтверждая карточку, выберите разовый платёж либо существующий платёж и его период. Это не меняет расписание и не отмечает оплату. При совпадении с регулярным платежом автоматическое создание останавливается до выбора пользователя. Для надёжного сопоставления укажите связанный регулярный платёж в шаблоне; поиск похожего названия — лишь подсказка.

## Обучение поставщику

Всё находится в Настройки → Распознавание счетов → Поставщики и обучение.

Добавьте шаблон: точный отправитель, при необходимости фраза в теме, подтверждённые название/ИНН/банк/счёт/валюта. Затем задайте подписи перед нужными значениями. Пример для суммы: `Всего к оплате`. Значение берётся справа от подписи или со следующей строки. При нескольких разных совпадениях поле считается неоднозначным. Если справа есть другое поле, используйте границу: `Всего: => НДС`. Это буквальные подписи, не программные скрипты.

Выберите сохранённый пример, откройте его текст и «Проверить правила на примере». Проверка не создаёт платёж. Подписи дополняют общие русские/английские правила. Шаблон не заполняет отсутствующую валюту или новые банковские реквизиты ожидаемыми значениями. Для отсутствующего срока можно задать число календарных/рабочих дней от даты счёта; карточка отмечает рассчитанный срок. Рабочие дни берутся из календаря компании.

Включите автоматическое создание только после проверки примера. При единственном подходящем шаблоне, подтверждённом отправителе, однозначных обязательных полях, достаточной оценке OCR и прошедших проверках создаётся отдельный неоплаченный разовый платёж. Изменившиеся реквизиты, несколько подходящих шаблонов, недостающие поля, пометка оплаты/корректировки или пересечение с регулярным платежом остаются на проверке. Для иностранной валюты требуется её явное присутствие в документе и совпадение с шаблоном; автоматической конвертации в рубли нет. Рублёвое числовое поле прежних платежей не используется для AED/USD/EUR и т. п.

«Применить правила к ожидающим» перепроверяет до 50 ожидающих документов за один запуск. Уже созданные платежи не переписываются. Если после уточнения полей обнаружится существующий счёт, новый платёж не создаётся: запись помечается дубликатом. Первоначально неподтверждённый отправитель не получает доверия задним числом от изменения шаблона — такой счёт подтверждается вручную.

## Дубли и архив

Проверяются ключ IMAP, хеш файла и поставщик/номер/дата/сумма/валюта. Повтор/пересылка не создают новый платёж. Разные файлы одной подтверждённой копии сохраняются как альтернативные оригиналы. При тех же номере, дате и сумме, но других банковских реквизитах документ сохраняется отдельно и требует проверки. Исправление суммы при том же номере также требует проверки. Статус «Пропустить» сохраняется, повтор того же файла его не возвращает.

Очередь показывает до 2000 последних записей с приоритетом ожидающих; старые документы платежа запрашиваются отдельно по PaymentId, поэтому скачивание из строки не зависит от этого ограничения. История обработки ограничена последними 1000 сообщениями. Документы не удаляются настройкой хранения отчётов бэкапа. Удаление платежа не удаляет исходный счёт из архива.

## Форматы, ограничения и установка OCR

Текстовые PDF читаются PdfPig. Для PNG/JPEG и сканов используется локальный Tesseract с русской и английской моделями. Нет LLM, внешнего сервиса распознавания или отправки документов в облако. OCR сам использует обученные модели; «обучение поставщику» в интерфейсе означает сохранение правил извлечения полей.

Модели включены в исходную сборку и копируются на сервер; каждый раз скачивать их не надо. Нативный OCR только для Windows x64; нужны библиотеки Microsoft Visual C++ 2019 или новее. PUBLISH предлагает включить официальный VC++-установщик, кэширует его в RuntimePackages и проверяет подпись Microsoft. При новой установке/обновлении серверный GUI-установщик устанавливает его при необходимости. Выбор .NET Runtime независим. Если отказаться от VC++ и его ещё нет на сервере, текстовые PDF продолжат работать, а сканы останутся на проверке с ошибкой OCR. Возможна штатная необходимость перезагрузки Windows после установки VC++.

До 8 МБ на файл, до 16 МБ на письмо, до 8 файлов на письмо, до 10 страниц PDF; до 100000 символов текста. Больше и неподдержанные вложения отмечаются в истории. Читаются PDF/PNG/JPEG по сигнатуре содержимого, ZIP/Office/макросы не запускаются и не распаковываются. Парольные, составные или необычно закодированные PDF могут потребовать ручной проверки. Для сканов PDF извлекаются встроенные изображения; это не универсальный рендерер всех PDF-конструкций и фильтров. При ошибке чтения принятого PDF оригинал сохраняется в очереди.

Извлечение выполняется отдельным процессом, последовательно, с таймаутом 60 секунд. На Windows применён Job Object с лимитом памяти 512 МБ, запретом дочерних процессов и завершением при закрытии родителя. Это ограничение ресурсов, **не полноценная песочница безопасности**. Не следует считать вложения доверенными только потому, что программа извлекла из них текст. Скачать оригинал вправе пользователи с чтением раздела Счета, подтверждать — с изменением. Настройки требуют прав изменения настроек, работа с обучающими документами дополнительно требует доступа к счетам.

## Значок Windows Update

Сервер учитывает положительный PendingCount, восстанавливает отсутствующую проекцию из последнего отчёта агента, а клиент раз в 20 секунд точечно обновляет значок на главной и в устройствах, не перестраивая страницу или открытую форму. Ошибка проверки не стирает последнее известное наличие обновлений; подтверждённое Current без ожидающих обновлений и без необходимости перезагрузки скрывает значок. Цвет устройства и уведомления Telegram из-за обновлений не меняются. Требуются сервер и клиент 0.30.1; если агент уже присылает результаты Windows Update, переустановка агента не нужна.

Проверки и ограничения среды — verification/AUDIT.md. Полноценный Windows OCR/GUI/IMAP и SQL Server в среде разработки не запускались; перед включением автообработки проверьте пример вашего поставщика.

# Агент мониторинга Linux

Обновление существующего агента без переустановки: [LINUX_UPDATE_0.32.md](LINUX_UPDATE_0.32.md). В 0.32 добавлены отдельные пороги /boot/EFI, inode и корректный контроль oneshot/таймеров.

Агент предназначен для Debian и Ubuntu x64 с systemd. Он собирает показатели, которые читает служба мониторинга; на сервере нужен SysAdmin Assistant той же версии. Доступ на вход к Linux-агенту не требуется.

1. Обнови сервер и клиент Assistant этой версии.
2. В «Устройствах» создай или открой устройство, перейди на вкладку «Агент» и нажми «Установить Linux». Одноразовая команда копируется в буфер; она действует 15 минут.
3. Подключись к Debian/Ubuntu по SSH и вставь команду целиком. Для установки необходим root или sudo. Если curl отсутствует, сценарий попробует установить его через apt.
4. После регистрации в карточке Assistant сверь отпечаток ключа с тем, что выводит `sudo cat /var/lib/sysadminassistant-agent/status.json`, и нажми «Подтвердить». Только после этого сервер принимает отчёты.
5. В карточке настрой «Пороги», «Пороги сети» и «Роли и службы». Можно добавлять отдельные службы и исключать ненужные.

Агент передаёт загрузку CPU и RAM, swap, место на доступных файловых системах, uptime, скорости сетевых интерфейсов, состояние выбранных служб и сведения из локального кэша APT. Он не запускает поиск, установку обновлений, команды администрирования и изменения служб по запросу сервера. Исполняемый файл агента включён в пакет сервера; SDK и .NET на целевом Linux-сервере не нужны.

В «Журналах» настраиваются события Linux: ошибки памяти и диска, ядра, аварийные остановки служб и серия неудачных SSH-входов. Сбор начинается с момента первого подключения. Для доступа к системному журналу установщик добавляет учётную запись saa-agent в группу systemd-journal. Она получает право читать системные журналы; агент передаёт только выбранные им категории. Если журнал недоступен, в состоянии отображается предупреждение.

Агент проверяет подпись обновления сервера и применяет его через отдельный systemd-таймер; при неудачном старте предусмотрен откат. Сертификаты агента продлеваются автоматически через сервер. Сервер и агент должны оставаться доступны друг другу по HTTPS.

Проверка состояния на Linux:

```bash
sudo systemctl status sysadminassistant-agent.service
sudo journalctl -u sysadminassistant-agent.service -n 100 --no-pager
sudo cat /var/lib/sysadminassistant-agent/status.json
```

Сначала проверь установку и обновление на тестовой виртуальной машине: проверка публикации на Windows и установка на реальном Debian/Ubuntu с systemd зависят от окружения.

# Обновление до 0.32.0 без переустановки агента

## Что найдено в 0.31.2

Сервер подписывал манифест на 10 минут. LinuxUpdateApply проверял срок через LinuxAgentRelease.Verify **до** сравнения версии и оставлял release.json/release.bin в активном staging как после успешной установки, так и после «Новая версия не требуется». Поэтому просроченный остаточный пакет повторно вызывал CryptographicException. Исполняемый файл при этом мог полностью совпадать с release.bin.

Механизм воспроизведён на исходниках 0.31.2 в отдельном временном каталоге: сначала «не требуется» и сохранённая очередь, затем CryptographicException с истёкшим подписанным манифестом при одинаковых бинарных файлах. Это подтверждает дефект исходников и объясняет предоставленную последовательность 29.10.2026. Сам манифест с рабочего узла не исследовался: конкретный экземпляр ошибки нельзя считать доказанным только по совпадению SHA256.

В 0.32.0 подпись и принадлежность агенту проверяются всегда. Просроченный пакет **не устанавливается**. Уже установленный подлинный пакет можно безопасно вывести из очереди, не исполняя его повторно. SHA256 не заменяет проверку цифровой подписи.

## Порядок обновления

1. Сохрани штатную резервную копию SQL-базы сервера и каталога данных Assistant. Не запускай CLEANUP/REMOVE/деинсталлятор.
2. Распакуй исходники и запусти PUBLISH.bat на Windows с .NET SDK 10. Перенеси ServerSetup целиком. В SETUP_SERVER.cmd выбери обновление установленного сервера. Оно сохраняет БД, конфигурацию, сертификаты и регистрацию; SQL-копию установщик за тебя не делает.
3. Обнови клиент из той же публикации. В старом клиенте новые поля карточки Linux могут быть недоступны.
4. Сервер должен содержать AgentTemplate/Linux/SysAdminAssistant.AgentLinux из этой же публикации. Не создавай заново установщик для уже зарегистрированного устройства: это не способ обновления агента.
5. Работающий Linux-агент 0.31.2 сам запросит новый подписанный выпуск. До обновления ему отправляется совместимая политика без неизвестных JSON-полей. Обычно проверка выполняется раз в час, применение — таймером примерно раз в пять минут.
6. Если таймер был остановлен при диагностике, после обновления сервера верни его:

```bash
sudo systemctl enable --now sysadminassistant-agent-update.timer
```

Чтобы не ждать очередного часового запроса, можно один раз перезапустить **основную** службу; регистрация не удаляется:

```bash
sudo systemctl restart sysadminassistant-agent.service
```

Это кратко прерывает сбор показателей. Не нужно удалять identity.json, bootstrap.json, каталог агента или его учётную запись.

7. В карточке дождись версии 0.32.0.0 и свежего отчёта. Если текущая активная очередь всё ещё содержит старый просроченный пакет и старый обновлятор не может перейти на новый выпуск, сохрани её в карантине по прежней процедуре, не возвращая файлы из карантина в активный staging. В вашем случае каталог update-staging.quarantine.20261029-081355 уже сохранён; его программа не трогает.
Если именно **старая 0.31.2** снова зациклилась на активном staging, ниже одноразовый запасной способ. Он не нужен, если обновление идёт штатно. Сначала обнови сервер. Скрипт кратко останавливает сбор показателей, переносит очередь целиком в новый карантин и возвращает службы; данные регистрации не меняет. Если привилегированная установка ещё выполняется, он отказывается трогать файлы: дождись её завершения.

```bash
sudo bash <<'BASH'
set -euo pipefail
systemctl stop sysadminassistant-agent-update.timer
if systemctl is-active --quiet sysadminassistant-agent-update.service; then
  echo 'Обновлятор ещё выполняется. Очередь не менялась; повтори после завершения.'
  systemctl start sysadminassistant-agent-update.timer
  exit 1
fi
trap 'systemctl start sysadminassistant-agent.service; systemctl start sysadminassistant-agent-update.timer' EXIT
systemctl stop sysadminassistant-agent.service
queue=/var/lib/sysadminassistant-agent/update-staging
if [[ -e "$queue" || -L "$queue" ]]; then
  quarantine="$queue.quarantine.$(date -u +%Y%m%d-%H%M%S).$$"
  mv -T -- "$queue" "$quarantine"
  printf 'Очередь сохранена: %s\n' "$quarantine"
else
  echo 'Активной очереди нет; ничего не переносилось.'
fi
BASH
```

8. Только после перехода агента на 0.32.0 доступны inode, типы systemd и подробные сведения о ФС. Базовые безопасные пороги /boot сервер применяет и к старому отчёту, если точка была передана.

## Проверка результата (без изменений системы)

```bash
sudo systemctl status sysadminassistant-agent.service
sudo systemctl status sysadminassistant-agent-update.timer
sudo systemctl show sysadminassistant-agent-update.service -p Type -p ActiveState -p SubState -p Result -p ExecMainCode -p ExecMainStatus
sudo journalctl -u sysadminassistant-agent-update.service -n 100 --no-pager
sudo cat /var/lib/sysadminassistant-agent/status.json
sudo cat /opt/sysadminassistant-agent/update-result.json
```

Для oneshot успешный Result=success и код 0 с inactive/dead — норма. Активность таймера проверяется отдельно от последнего результата службы. Файл update-result.json описывает **доставку пакета**, поэтому успешный запуск без пакета не стирает прежнее отклонение подписи/хэша. Его закрывает проверенная установка либо свежий подписанный манифест, подтверждающий установленный файл; ошибка более новой версии не закрывается подтверждением более старой.

Не присылай bootstrap.json, identity.json, приватные ключи или токены. В status.json и update-result.json их нет.

## Транзакция и диагностика

- Загрузчик публикует целый каталог пакета атомарным переименованием. Загрузчик и обновлятор блокируют один стабильный inode каталога данных через flock.
- Обновлятор атомарно забирает каталог в claimed. Проверка файлов выполняется через openat/O_NOFOLLOW относительно удерживаемого дескриптора; подмена промежуточного каталога не даёт удалить или прочитать произвольные файлы привилегиями root.
- Подготовленный файл, резервная копия, маркер и квитанция завершаются с flush/fsync. Предыдущий файл остаётся agent.previous. После сбоя запуска выполняется откат; незавершённая транзакция восстанавливается по root-маркеру и квитанции.
- Начиная с 0.42.8 обновлятор удаляет отклонённый пакет после записи результата. Детали и история — update-result.json, update-history.ndjson и предыдущий сегмент update-history.ndjson.previous в каталоге программы. Резервный бинарник agent.previous сохраняется для отката.
- Пустые consumed-каталоги могут сохраняться как след завершения. Они не являются очередью и повторно не исполняются.

## Диски и службы

В карточке агента: «Тома и пороги». Для /boot по умолчанию 10% свободного или 128 МиБ, для EFI — 5% или 32 МиБ; на очень маленьком разделе стандартный абсолютный минимум ограничивается 10% ёмкости. Индивидуальное правило точки имеет приоритет. Для остальных ФС остаются общие пороги устройства. Inode контролируются отдельно (обычно 5% свободных); неизвестные inode не подменяются нулём. Swap-порог по умолчанию отключён и включается явно.

В «Роли и службы» можно мониторить .service и .timer. Для oneshot нормой считается успешное завершение, а не вечный Running. У таймера контролируются активность и связанное задание. Ожидаемый интервал задаётся отдельно; отсутствующее расписание не выдумывается. Для периодических задач/календарных таймеров укажи максимальный допустимый интервал выполнения, если нужен контроль пропусков.

«История проверок» хранит метрики и переходы со счётчиками наблюдений. Это число подтверждений состояния опросом, а не число исполнений процесса. Фактические попытки доставки и время её ошибок указаны отдельно в UpdateDelivery, а журнальные повторы считаются по уникальным событиям; «Полная история журнала» показывает архив страницами. В каталоге данных сервера создаются agent-metric-history, linux-event-history/windows-event-history и linux-problem-history/windows-problem-history. Прежние данные сохранены; архив новых событий и сохранившихся старых записей дополняется, без автоматического удаления. Включи эти каталоги в резервное копирование и план контроля объёма.

## Расписание
- В форме задания настройка «Допуск ± N минут». Например, 21:00 ±120 — с 19:00 до 23:00 включительно.

# 0.10.0 — разбор писем и открытые проблемы устройств

- В задании и таблице резервного копирования добавлена «Система бэкапа». Можно выбрать систему из словарей или автоопределение.
- В устройстве добавлен «Словарь писем устройства». При автоопределении и отсутствии признаков в письме тип QNAP NAS использует QNAP, Synology NAS — DSM. Явная система задания имеет приоритет над словарём устройства.
- Привязка письма повторно анализирует сохранённый текст по текущему словарю: результат, критичность, доказательства и рекомендации. Такой же анализ выполняется для следующих писем по правилу.
- «Разобрать письма» в устройствах и заданиях повторно обрабатывает уже привязанные письма. При изменении выбранной системы у существующего объекта клиент запускает повторный разбор, если есть право изменять отчёты. Для ручного повторного разбора нужны права изменения соответствующего раздела и отчётов.
- В резервном копировании отображаются только созданные задания. Обычные письма устройства, в том числе QNAP HBS и Veeam, не создают задание автоматически.
- Цвет устройств в реестре и на главной учитывает все открытые критические события и предупреждения любого источника. Устройства с проблемами стоят выше.
- Карточка устройства открывает вкладку «Проблемы», если есть события. Видны количество, дата, источник, причина и основание анализа. Двойной щелчок / «Открыть письмо» открывает исходное письмо.
- «Решено» закрывает ровно одно выбранное событие; нужны право изменения отчётов и доступ к устройству. Пока есть хотя бы одно критическое событие, цвет красный. Только предупреждения — жёлтый. Когда событий нет, цвет определяется доступностью и сервисами: исправное устройство зелёное, недоступное остаётся красным. Архив и режим обслуживания сохраняют свой специальный статус.
- Обычное последующее информационное письмо не снимает старую тревогу. Повторный анализ не открывает закрытые события и не дублирует их. Новое критическое письмо создаёт новую проблему.
- Критичность устройства и результат бэкапа различаются. Системное уведомление QNAP может быть «Событие / Критично», без выдуманного результата резервного копирования.
- Нераспознанный результат показан явно. Совпадение фраз привязки не означает успеха. Если исходный текст старого письма недоступен, повторный анализ не восстановит его из ничего.
- Добавление столбцов сохраняет существующие данные SQLite и SQL Server; экспорт/импорт переносит выбранные словари. Сервер и клиенты необходимо обновить вместе.

# Привязка писем и повторные запуски

## Быстро привязать одно письмо
В Отчётах выбери письмо и нажми «Привязать», либо нажми правой кнопкой по строке → Привязать.
Эта же кнопка есть в открытом письме. Для DMARC привязка к устройству/бэкапу не применяется.
Выбери устройство или задание. Если автоматическое правило не отмечено, изменится только выбранное письмо.
У нераспознанного результата цель сохранится, но письмо останется в очереди до разбора результата — программа не придумывает успешный бэкап.

## Правило по нескольким строкам
1. В окне привязки, вкладка «Письмо и строки», выдели постоянную строку текста и нажми «Добавить выделенное в условия».
2. Повтори для других строк. Можно также вписать условия вручную: одно на строку, до 32.
3. Выбери «Все строки (И)» либо «Хотя бы одна строка (ИЛИ)».
4. На вкладке «Цель и применение» отметь автоматическую привязку следующих писем.
5. При необходимости отметь применение к старым письмам.
6. Нажми «Показать совпадения», проверь количество и первые 30 примеров.
7. Подтверди кнопкой «Привязать».

Пример И:
Host: NAS-A
Task GUID: tenant-A
Подойдут письма, содержащие обе строки. Host: NAS-B с таким же отправителем и темой не подойдёт.
Пример ИЛИ:
Task GUID: current-name
Task GUID: legacy-name
Подойдёт одна из альтернатив для выбранного задания.

Регистр не важен; пустые строки и повторяющиеся условия игнорируются. Это буквальное вхождение текста. Символы * и ; не являются специальными разделителями или регулярными выражениями.
Новое правило из письма проверяет только строки тела; скрытых ограничений по теме, отправителю и источнику нет. DMARC обрабатывается отдельно.
В старом редакторе правил можно отдельно сочетать тему, отправителя и группу строк тела.

Чужие существующие привязки по умолчанию не меняются. Для их замены есть отдельная галочка; после её изменения нужно повторить просмотр.
Если другое активное правило совпадает с теми же письмами и задаёт другую цель или другой принудительный результат, будут показаны номера конфликтующих правил. Автоматическое правило не сохранится до устранения конфликта. Привязка только одного письма остаётся доступна.
Если письма/правила поменялись после просмотра, сохранение просит обновить просмотр и не делает частичных изменений.
У старых распознанных писем может не быть исходного текста; такие записи пропускаются и считаются отдельно. Сверка с IMAP и открытие сохранившегося письма позволяют дочитать его текст.

## Один бэкап дважды в день
Задания бэкапов → Изменить → ожидаемые завершения:
09:00; 21:00
До 24 времён в сутки. Дни недели и допуск общие для задания; допуск должен быть меньше интервала между запусками.
На главной и в заданиях показаны отдельные строки для каждого времени.
Правило по строкам определяет задание, а время выполнения внутри отчёта — запуск. При отсутствии времени отчёта используется поступление IMAP, затем заголовок, если IMAP-дата неизвестна; источник времени отмечается в разборе.
Утренний отчёт не закрывает вечернее ожидание. На границе допуска один отчёт засчитывается только одному автоматическому окну.
При ручной привязке можно явно выбрать запуск для выбранного письма. Для массово привязываемых прошлых и будущих писем запуск определяется автоматически.
Время, назначенное вручную, не закрывает другой запуск. Изменение расписания начинает новую точку контроля, как и в прежней версии.

# Почему не отображаются письма

Проверки выполняет сервер, а не компьютер клиента. Приложение не является полноценным почтовым клиентом: оно сохраняет принятые отчёты и не показывает весь INBOX без фильтрации.

1. Настройки → Почта / IMAP → Почтовые ящики → Изменить → «Проверить подключение к ящику». Проверяются реальные несохранённые адрес, порт, логин и папка. Проверка не сохраняет форму. При успехе видны TLS, вход, папка и число писем.
2. Сохрани ящик, включи «Принимать отчёты». Для первоначальной проверки выбери «Все письма»: уже прочитанные письма не попадут в поиск «Только непрочитанные».
3. Для обычных отчётов укажи точные домены From, по одному на строку, например example.test. Не адрес получателя и не полный email. Поддомены отдельно. Пустой список блокирует обработку с явной ошибкой.
4. Нажми «Проверить почту сейчас» в Отчётах или Настройках. Это запуск в очередь; сообщение о запуске не означает завершение. Открой «Диагностика почты» и обновляй результат.
5. Смотри Отчёты → Все и Нераспознанные. Для неизвестного источника и письма без правила SQL-задание не требуется. Ошибки формата DMARC находятся в DMARC → Ошибки DMARC.

## Как понимать результат

| Показатель | Что проверять |
| --- | --- |
| Проверок ещё нет | Служба запущена, ящик сохранён и включён; запусти проверку и обнови результат |
| TLS-соединение / ошибка | DNS и доступ сервера к IMAP, правильный TLS-порт (обычно 993), сертификат, системное время |
| Вход в ящик / ошибка | Логин, пароль приложения почтового провайдера, разрешение IMAP. Пароль вводится в форме, передавать его в чат не нужно |
| Открытие папки / ошибка | Точное IMAP-имя папки, права на неё; начни с INBOX |
| Найдено 0 | Не та папка, режим только непрочитанных; у DMARC также поиск темы DMARC |
| Уже учтено | Эти UID уже импортированы или удалены по сроку хранения. Повторный опрос не дублирует их |
| Фильтр отправителя/темы | Сверь домен From со списком. Обычный ящик исключает темы со словом DMARC; DMARC требует подтверждённого полного адреса и темы DMARC |
| SPF/DKIM отклонено | При включённой проверке нужны оба pass от доверенного принимающего MTA, правильный authserv-id и подтверждённая очистка поддельных заголовков. Это не повторный расчёт подписей приложением |
| Без текстового тела | Вложения обычных отчётов намеренно не читаются. Теперь заголовок и объяснение сохраняются в нераспознанной очереди |
| Без заголовков | Сервер IMAP не вернул Envelope запрошенного UID; письмо могло быть удалено другим клиентом во время опроса |
| Без подходящего содержимого | Для DMARC не найден допустимый XML/архив. Обычное письмо не превращается автоматически в DMARC |
| Принято, отчётов 0 | Возможна дедупликация по содержимому DMARC или уже существующий результат. Проверь старые записи и дату |
| Ящик уже проверяется | Активен другой цикл/процесс; временная блокировка истекает через две минуты без продления |

На подготовленных ранее снимках были включены «Все письма» и мониторинг, а SPF/DKIM был выключен. Поэтому эти три настройки сами по себе не объясняют именно тот случай. Исправлены найденные дефекты кода: зависимость IMAP от общей галочки мониторинга, выбор случайной сводки вместо точного UID, обход старых писем раньше новых, молчаливый пропуск без текстовой части и отсутствие промежуточных результатов. Проверка на рабочем IMAP-сервере ещё нужна.

Чтение остаётся read-only, флаг прочтения не меняется. Защита TLS, фильтры допуска и лимиты вложений не отключены. Полные письма автоматически не скачиваются.

# Письма об обновлениях

1. В существующих словарях открой «Обновления». Встроенные DSM / QNAP получают типовые фразы один раз; правки пользователя не перезаписываются. Для своего продукта укажи название и буквальные фразы темы и/или тела.
2. В почтовом списке выбери письмо → «Привязать» → «Уведомление об обновлении». Выбери устройство и продукт. Для будущих писем добавь строки темы / тела с И/ИЛИ, посмотри предварительный просмотр и сохрани правило. По одному адресу отправителя автоматического назначения устройства нет.
3. У устройства появляется отдельный значок обновления. Наличие новой прошивки не меняет красный/жёлтый/зелёный статус и не создаёт задание бэкапа.
4. Нажми значок: видны продукт, версия, даты первого / последнего письма, исходное письмо и история. «Установлено» — ручное подтверждение фактической установки с записью пользователя и UTC-времени, без запуска обновления. Для чтения письма нужна роль «Отчёты», для подтверждения — редактирование соответствующего раздела устройств / коммутаторов.

DSM извлекается целиком, например `7.4.1-90080 Update 1`, включая суффикс Update. QTS / QuTS hero поддержаны типовыми шаблонами. Если версии нет или в письме несколько разных версий, не угадываем: отметка относится к тексту письма; посмотри источник вручную. Для произвольного формата версии может потребоваться расширение шаблона.

Одна версия одного продукта и устройства даёт одно предупреждение в общей очереди уведомлений Telegram с действующими фильтрами. Повтор не создаёт новую запись. После «Установлено» повтор той же версии не возвращает значок; другая версия создаёт новую запись. История подтверждений хранится с устройством и переживает удаление исходных писем по сроку хранения; исходное письмо после удаления открыть нельзя. Лимит истории — 1000 версий, превышение отправляет письмо на ручной разбор.

Письмо сообщает о доступности обновления, но не доказывает состояние NAS. Сведения прямого опроса ОС / RouterOS показываются отдельной вкладкой и имеют собственную актуальность. Настройки IMAP, допуск отправителей и проверка безопасности письма остаются прежними. Для этой возможности обнови сервер и клиент; агент на NAS не требуется.

# Доверенные сети и показатели устройства · 0.33

## Изменение сетей

Главный администратор: Настройки → Сервер → Доверенные сети. Одна частная подсеть CIDR на строку, например 192.168.20.0/24. Сохранение сразу меняет доступ на уровне приложения; переустановка не нужна. Loopback остаётся разрешённым для локальной диагностики. Список защищает и клиентов, и входящие соединения агентов.

Windows Firewall — второй независимый уровень. Если у службы нет прав администратора (нормально для выделенной учётной записи), после сохранения появится соответствующее сообщение и готовая команда PowerShell. Выполни её **на сервере от администратора**. Без этого новая подсеть может оставаться заблокированной Windows Firewall. Не отключай firewall целиком. Если штатное правило отсутствует или управляется доменной политикой, требуется проверить его на сервере; программа не создаёт разрешение на весь трафик.

Если исключаешь адрес текущего клиента, приложение отдельно запросит подтверждение. Сначала добавляй новую сеть и проверяй подключение оттуда, только потом удаляй старую. Два администратора не могут незаметно перезаписать изменения друг друга.

Рабочий список: каталог данных сервера/trusted-networks.json. Предыдущий: trusted-networks.json.previous. При ошибочном подтверждённом отключении доступ можно восстановить локально на сервере: остановить службу SysAdminAssistantServer, вернуть предыдущий файл под именем trusted-networks.json, запустить службу; затем проверить адреса штатного правила Windows Firewall. Это не требует удаления БД. Добавь оба файла в обычную резервную копию каталога данных. При отсутствии override используется исходный список server.json. Повреждённый override не игнорируется в пользу более широких разрешений.

«Разрешённые подсети назначения» в установщике агента — **другая настройка**: куда самому агенту разрешено подключаться. Изменение доверенных сетей сервера не расширяет эти ограничения автоматически и не меняет сертификаты, регистрацию, маршруты или firewall на других устройствах.

## Полоски показателей

Устройства → карточка → Агент. CPU, RAM, Windows-диски с буквами или Linux-точки /, /boot и другие, swap (если существует), сетевые интерфейсы. Полоска диска показывает занятое пространство; доступный остаток подписан отдельно. На Linux зарезервированные блоки ФС отдельно объясняются в подробностях, поэтому «занято + доступно» не всегда равно полному размеру. Порог диска проверяет остаток, не цветовую границу, нарисованную на глаз.

Подробности и пороги открывают факты и рекомендации. Изменение условий — кнопки «Пороги», «Тома и пороги», «Пороги сети» в той же карточке. Цвет реагирует на настроенные условия. Отключённый контроль не является подтверждением отсутствия проблем; его состояние указано в подробностях.

Панель опрашивается каждые 10 секунд; сам агент передаёт с заданной периодичностью. Серым помечаются данные старше max(90 секунд, три интервала передачи), отсутствующая связь или отозванный доступ. CPU-график хранит до 60 новых измерений только пока карточка открыта, повтор одного отчёта не добавляет точку.

Для сети: приём/передача в байтах в секунду, скорость канала в битах в секунду. Процент — более загруженное из двух направлений, а не их сумма. Если скорость неизвестна, процент не выдумывается; реальную пропускную способность можно задать в «Пороги сети». Первый сетевой замер нового Windows-агента нужен для получения базы счётчиков, скорость появляется со следующего отчёта. Для виртуальных NIC скорость драйвера может отличаться от реального WAN — используй ручную настройку.

Новая панель требует обновления сервера и клиента. Для сетевых показателей Windows нужен агент 0.33; дождись его подписанного автообновления. Старые агенты не получают команд управления и сохраняют прежнюю регистрацию. Не переустанавливай их ради оформления интерфейса.

## Пароли сервисов

В «Пароли» открой запись на изменение и выбери «Связать с сервисом». Можно оставить одновременно связь с устройством. В таблице появилась колонка «Сервис» и переход к его данным. Во вкладке «Сервисы» выбери строку и нажми «Пароли сервиса»: если доступных записей несколько, появится выбор, затем обычное окно секрета с подтверждением доступа.

Права на сервис не дают права на чужой пароль. Требуется разрешение «Пароли», собственная доступная запись и стандартная разблокировка. Назначение новой связи также требует доступа к «Сервисам». Переименованный сервис сохраняет связь по ID. Перед удалением сервиса нужно снять привязку; пароль автоматически не удаляется.

В Excel добавлена колонка «Сервис ID». Для нового шаблона пустая ячейка снимает связь. Старый семиколоночный шаблон остаётся допустимым и при обновлении существующей записи сохраняет её прежний ServiceId. Перенос БД переназначает ID сервиса вместе со связью. Обновление добавляет nullable-столбец в существующую таблицу паролей (SQLite/SQL Server), шифрование секретов и старые поля не меняет. Перед обновлением сделай обычную резервную копию БД; чистая установка не нужна.

## Проверка

Полная сборка и тесты доступны через VERIFY.cmd/PUBLISH.bat. Результаты этой версии — verification/AUDIT_0.33.md. Windows GUI и изменение настоящего Windows Firewall в Linux-среде не запускались; это ограничение проверки, а не подтверждение работоспособности любой доменной политики.

# Сеть, правила и Telegram · 0.10.0

## Общий редактор
В разделе «Коммутаторы / сеть» выбери MikroTik и нажми «Правила». Таблица одинакова для любых площадок: одна строка — одно правило. В интерфейсе нет специальных полей для Москвы/Петербурга. «Добавить», «Изменить», «Копировать», «Удалить», включение и настройки Telegram доступны пользователям с правом изменения раздела сети.

В правиле выбираются:
- тип: состояние интерфейса или сообщение в логе;
- важность и включение;
- для интерфейса: точные имена, фразы комментариев, задержка, число успешных опросов;
- для лога: буквальные фразы И/ИЛИ, темы RouterOS (любая), исключения (любое), порог и окно, группировка по IP из `from …` или по всем источникам;
- предшествующие фразы/число совпадений для корреляции (например, успешный вход после отказов);
- группа повышения важности: одинаковый ID объединяет связанные правила в одну проблему с повышением важности;
- закрытие после заданного периода без повторов или вручную, отправка в Telegram и сообщение о закрытии.

Имена интерфейсов переносятся из ранее выбранного словаря и старых назначений. Свои сохранённые наборы не перезаписываются будущим импортом профиля. Чтобы применить обновлённый профиль заново, явно выбери замену набора в редакторе. Сохранение пустого набора выключает пользовательские правила; контроль доступа к API и чтения логов остаётся системной проверкой.

## Стандартные правила
| Событие | Уровень / порог | Закрытие |
|---|---|---|
| Неверный пароль | Информация: 1 попытка | Тишина 3600 с |
| Повторные неверные пароли | Предупреждение: 5 за 300 с с одного IP | Тишина 3600 с |
| Возможный перебор пароля | Критично: 20 за 300 с с одного IP | Тишина 3600 с |
| Успешный вход после отказов | Критично: после 5 отказов за 600 с с того же IP | Вручную |
| Вход в управление | Информация | Тишина 60 с |
| Изменена конфигурация | Предупреждение | Вручную |
| Любая обнаруженная перезагрузка | Критично | Вручную |
| Ошибки памяти, ядра, накопителя | Критично | Вручную |
| Проблемы питания, вентилятора, температуры | Критично | Вручную |
| Недостаток места на накопителе | Предупреждение | Вручную |
| Ошибки сертификата / SSL | Предупреждение: 3 за 300 с | Тишина 900 с |
| Сообщение о SYN flood / сканировании | Предупреждение | Тишина 900 с |
| Другие сообщения с темой critical | Критично, с исключениями для отдельных правил | Вручную |

Это редактируемые шаблоны буквальных сообщений. Наличие события и формулировка зависят от RouterOS и настроек его logging; это не полный словарь всех ошибок производителя. Записи должны быть доступны в `/log` через API. Программа только читает RouterOS и не включает логирование/правила firewall на устройстве. Обычное отключение VPN-пользователя само по себе не становится критическим.

Перезагрузка дополнительно определяется по уменьшению uptime между успешными опросами. Это не устанавливает её причину. Если соответствующая информация не попала ни в доступные логи, ни в наблюдаемое уменьшение uptime, приложение не может доказать перезагрузку.

Первый буфер логов при подключении/переходе на новую обработку отмечается как история. Он не создаёт массовые старые тревоги и не участвует в счётчиках. Последующие новые записи дедуплицируются. Окно повторов использует время обнаружения на сервере; исходное время RouterOS показывается отдельно. Хранятся последние 1000 уникальных записей и до 2000 закрытых проблем плюс активные.

## Закрытие и доставка
«События → Активные проблемы → Решено» закрывает выбранную проблему лога и сбрасывает её счётчик. Другие проблемы остаются. Интерфейсы закрываются только после подтверждённого восстановления. При ошибке API или чтения логов прежние проблемы не считаются восстановленными.

Все подключения Telegram используют общие настройки уровней. Закрытие сетевой проблемы относится к исходному уровню проблемы. Уведомления ставятся в постоянную очередь один раз на переход/повышение важности, повторяются после ошибки доставки и сохраняются при перезапуске. Полный текст логов и пароли в сообщения не отправляются. Получателями Telegram управляет администратор; все включённые уведомления идут в заданный общий чат.

Сетевые события, ICMP, сервисы, DNS/интернет, ошибки IMAP, отсутствие/нераспознанность отчётов и счета подключены к общей доставке. Результаты полученных писем отправляются существующим механизмом событий отчётов. Напоминания о счетах не доставляются в выходные; очередь сетевых тревог не блокируется отложенными счетами.

Состояние и защищённые подключения — `network-state.json`, профили — `network-dictionaries.json` в каталоге данных сервера. GUI-обновление копирует весь каталог. Пароли соединений защищены DPAPI и связаны с машиной. Копия только SQL/SQLite не включает эти JSON-файлы.

Формат журнала и темы: https://help.mikrotik.com/docs/spaces/ROS/pages/328094/Log

# Анализ конфигурации MikroTik

## Использование

Коммутаторы / сеть → выбрать MikroTik → Анализ конфигурации. Либо открыть карточку двойным щелчком → Конфигурация. Нажми «Проверить конфигурацию», выбери строку. Доступны основания вывода, рекомендации и копирование команд. Исправления выполняет администратор вручную в RouterOS. Учётной записи мониторинга достаточно read + api; экспорт конфигурации, пароли, пользователи, скрипты и команды записи не запрашиваются.

Автоматический снимок конфигурации — раз в 15 минут в существующем соединении. Ручная проверка использует свежее соединение. Права на раздел «Коммутаторы» позволяют читать и запускать анализ; игнорирование / выбор WAN требуют редактирования раздела. Никакие пароли Vault для этого не нужны.

## Логика

- Input: новые TCP-соединения к включённым SSH, Telnet, FTP, WebFig, WinBox и API на фактически настроенных портах. Ограничение `/ip service address` пересекается с ограничениями firewall.
- DNS: TCP и UDP 53 при `allow-remote-requests=yes`. Общий запрет input / RAW может защищать DNS без отдельного правила 53.
- Forward: новые TCP-соединения на 3389 и 445 как проверка политики транзита, отдельно от наличия реального сервиса на хосте. Конкретные IPv4-пробросы проверяются для 22, 23, 53, 445, 3389, 5900, 8728, 8729, 8291 с учётом внешнего / внутреннего порта.
- Порядок правил, disabled, accept/drop/reject, jump/return, отрицание условий, src/dst CIDR, статические address lists и диапазоны, протоколы, порты, connection-state, connection-nat-state, входные/выходные интерфейсы и списки include/exclude. RAW проверяется до NAT; input/forward — после трансляции. Первый подходящий terminal action NAT исключает последующие трансляции.
- Established/related FastTrack не разрешает новый входящий сеанс. FastTrack, который матчится на новый сеанс, рассматривается как разрешение.
- IPv4 и IPv6 оцениваются отдельно. MAC WinBox / MAC server / neighbor discovery проверяются отдельно от IP firewall.
- Простое затенение: правило ниже безусловного завершения той же цепочки отмечается недостижимым. Для условных сложных правил доказательство полной недостижимости не заявляется.

Адреса источников рассчитываются интервалами, а не проверкой одного выбранного «внешнего IP». Ограниченный набор адресов показывается как допустимое ограничение, без автоматического объявления владельцев адресов доверенными. Очень широкое разрешение (не менее 1/16 пространства семейства) остаётся проблемой; исключение частных / запрещённых адресов не должно превращать открытый интернет-доступ в «безопасную белую выборку». Неподдержанный matcher не игнорируется.

WAN определяется по явным членам списка WAN и выходам активных маршрутов по умолчанию таблицы main. Имена интерфейсов и внутренние сети не зашиты. Если это не соответствует твоей топологии — выбери «Внешние интерфейсы», укажи точные имена по одному на строку. Пустое поле возвращает автоопределение. Для VPN default route, нестандартных таблиц и сложных списков выбор стоит проверить вручную.

## Игнорирование и уведомления

Игнорирование сохраняется для DeviceId + ключа проверки + отпечатка результата и релевантного пути правил, включая источники. Счётчики, комментарии и время опроса не меняют исключение. Изменение реальных условий требует нового решения. Исключения не переносятся автоматически на другой адрес устройства. Кнопка «Вернуть контроль» отменяет исключение; выключенные проблемы остаются видны фильтром.

Красный — есть активная критичная находка; жёлтый — предупреждение / неопределённость / устаревший анализ. Другие сетевые проблемы продолжают влиять на цвет. Отсутствие выполненного аудита не означает подтверждённую безопасность. Находки входят в общую очередь Telegram с действующими фильтрами важности; повторный неизменный снимок не создаёт дубликаты. Игнорирование/исправление отменяет ещё не отправленные уведомления этой находки.

## Ограничения

Это консервативный анализ снимка, не полная эмуляция RouterOS и не внешний пентест. Динамические / DNS address lists, rate/time/packet matchers, RAW notrack, add-to-list и неизвестные действия, диапазонная/сложная NAT-трансляция и неоднозначная маршрутизация дают «Нужна проверка». Не анализируются полностью bridge firewall, switch-chip ACL/L3 offload, mangle, policy routing, IPsec и conntrack уже существующих соединений. Поэтому результат описывает новый трафик на указанных входах в пределах прочитанных данных. Программа не доказывает доступность через роутер провайдера, DMZ или CGNAT.

До изменения конфигурации сверь текущий административный доступ, используй Safe Mode и резервную копию. Предлагаемые команды с TRUSTED_CIDR — шаблоны, пока не заменены твоими значениями; программа не подставляет домашние или офисные адреса.

Правила и обычные настройки ограничены отдельно: 1 млн символов, 2000 строк на меню, 5000 строк для интерпретации. Большие address lists в этот предел не входят. Загружаются только списки, указанные в активных IPv4/IPv6 правилах filter/raw/nat/mangle: API-фильтр по имени и только list/address/dynamic/disabled/timeout. Записи обрабатываются потоком и объединяются в точные непересекающиеся интервалы. Разрозненные адреса не заменяются широким CIDR.

Для списков: до 500000 исходных записей и 64 МБ API-ответа на список, до 128 используемых списков на семейство, до 500000 нормализованных диапазонов на семейство. Кэш разобранных множеств используется всеми проверками одного снимка. Операции пересечения / вычитания выполняются линейным проходом; полный набор адресов участвует в отпечатке игнорирования, даже если в карточке показаны только первые диапазоны. Динамические и DNS-списки по-прежнему требуют осторожной оценки. Предел анализа — 5 секунд, до 16 WAN, 32 локальных адресов и 512 шагов пути. При превышении выводится конкретное ограничение; неполные данные не объявляются безопасными.

# Контроль сервера через свой сайт

Сервер Assistant раз в минуту посылает подписанный HTTPS-сигнал PHP-приёмнику на твоём сайте. Cron на хостинге каждые 5 минут проверяет время последнего сигнала. После 5 минут без сигналов отправляется одна красная тревога; после восстановления — одна зелёная. Фактическое обнаружение занимает примерно 5–10 минут после последнего сигнала из-за шага cron. Задержки самого cron и Telegram могут увеличить срок.

Полная пошаговая установка: WebWatchdog/README.md. Пакет также копируется в Client/WebWatchdog и ServerSetup/WebWatchdog при PUBLISH.bat.

Наблюдатель должен находиться вне ДЦ мониторинга, иметь собственный работающий cron и исходящий доступ к Telegram. Если упадёт сам сайт/хостинг или его интернет, он тоже не сможет отправить сообщение. Не требуется VPN или публикация API Assistant наружу: запросы идут на сайт через обычный интернет.

Сигнал подтверждает запуск службы, чтение БД и исходящий путь до сайта; он не проверяет API из каждой клиентской сети. Пропажа сигналов — потеря связи/наблюдаемости, а не доказанный отказ всего ДЦ. При плановом обслуживании ставь maintenance=true на сайте и обратно false по окончании.

После обновления внешнюю проверку нужно настроить заново: HTTPS URL твоего PHP-файла, server_id и общий ключ. Старые параметры стороннего наблюдателя не используются, функция без нового адреса и ключа остаётся выключенной. Не отключай прежний реальный контроль до успешного теста новой схемы.

# Вход и персональные данные · 0.29.0

В окне подключения и повторного входа есть «Запомнить вход до закрытия приложения». По умолчанию галочка включена; её выбор сохраняется как предпочтение. Пароль и токен в connection.json не записываются.

С галочкой общие разделы работают без повторного ввода пароля, пока клиент остаётся подключённым. Фоновый запрос клиента поддерживает общий сеанс, даже когда окно свёрнуто в трей. Кратковременная потеря сети не требует пароля: клиент пытается восстановить соединение. После часа без подтверждённой связи (включая длительный сон компьютера) токен перестаёт действовать и требуется повторный вход. Показанная общая информация при отсутствии связи остаётся старым снимком, а не актуальными результатами.

Закрыть приложение означает «Выход» в трее; крестик может только скрыть окно в трей. После настоящего выхода и нового запуска нужен пароль. Токен существует только в памяти клиента. При штатном выходе выполняется короткая попытка отзыва на сервере; при аварийном завершении серверный токен истекает без обращений через час. При закрытии процесса клиент больше не может его использовать.

Если галочка выключена, сохраняется прежний общий сеанс с фиксированным сроком 8 часов. Его обычная активность не продлевает. После перезапуска службы сервера нужно снова войти — сеансы сервера не восстанавливаются с диска. Блокировка пользователя, изменение прав/пароля и выход отзывают доступ независимо от галочки. Переподключение не хранит и не подставляет пароль автоматически.

## Сотрудники и пароли

Общий вход не открывает персональные данные. «Инвентаризация» (сотрудники, выданное имущество и акты с ФИО) запрашивает отдельное подтверждение своего пароля на 5 минут. При уходе в другой раздел она закрывается; локальные строки инвентаризации удаляются из временной реплики. При истечении доступа открытый список закрывается после завершения работы с дочерним окном. Общие страницы по таймеру не перестраиваются. Перед новой загрузкой/операцией сервер всё равно проверяет разрешение и срок доступа.

Хранилище паролей использует независимую разблокировку на 5 минут, как прежде. Разблокировка сотрудников не открывает секреты и наоборот. Общий сеанс и его фоновое продление не продлевают эти 5 минут. Прежние правила просмотра/копирования секретов сохраняются.

В обычном снимке сервера нет сотрудников, имущества, актов и строк актов. Они возвращаются только по отдельному запросу разблокированной инвентаризации с правами на раздел. Это также относится к Excel сотрудников; шаблон без персональных данных доступен с правом чтения. Права разделов применяются дополнительно к разблокировке. Изменения служб, мониторинга, почты, счетов и устройств не требуют разблокировки персональных разделов.

Обновите сервер и клиент до 0.29.0. Агентов ради этого обновлять не нужно. Схема БД прежняя, сборка PUBLISH.bat. Проверки и ограничения — verification/AUDIT.md; визуальное поведение Windows и полный Windows NetworkSpecs здесь не запускались.

# Закреп активных проблем

Настройки → Telegram → «Закреплять список всех активных проблем». Функция включена по умолчанию. В закрепе критичные проблемы и предупреждения всех разделов, независимо от фильтров обычных уведомлений. Информационные записи и доступные обновления в закреп не попадают. Публикации MikroTik считаются группами. Игнорируемые и закрытые проблемы исключаются.

Обычно используется одно сообщение. Если список не помещается, создаются дополнительные страницы: проблемы не обрезаются молча. Сервер обновляет существующие страницы без звуковых уведомлений и снимает свой закреп с пустых страниц. Чужие закрепы не снимаются. ID сообщений сохраняются после перезапуска; если сообщение удалено, следующая попытка создаст замену.

В группах боту необходимо право can_pin_messages; в каналах — can_edit_messages. Ошибка прав не блокирует обычные уведомления. Статус закрепа доступен в настройках Telegram. При 429 учитывается retry_after. Смена чата тем же ботом снимает прежний управляемый закреп; при смене самого бота прежний закреп может потребоваться снять вручную. В случае сетевого обрыва в момент отправки Telegram не обеспечивает идемпотентность sendMessage: неподтверждённая отправка при повторе может оставить лишнее незакреплённое сообщение.

Обновление наблюдается примерно раз в 30 секунд плюс время запросов Telegram; это текущий список, а не гарантия доставки в реальном времени. При недоступном сервере или Telegram последнее сообщение может устареть. Обычная история событий сохраняется.

# Журналы и обновления ОС

Открой Устройства → карточка → Агент → Журналы Windows. Страницы не перестраиваются по таймеру; кнопка Обновить загружает новые записи вручную. Редактор «Правила и обновления ОС» управляет устройством отдельно. Профили SQL / AD / DNS добавляются вручную: установка роли сама по себе не включает дополнительный контроль. Правило использует точное системное имя Provider и числовые EventID; произвольные XPath или команды не принимаются.

Стандартные правила охватывают аварийные перезагрузки, BSOD, WHEA, ошибки NTFS/дисков, повторные падения приложений и служб, установку службы, нехватку памяти, неудачные входы, блокировку учётной записи, изменения групп и аудита, очистку Security, Defender и ошибки обновления. Изменение группы безопасности — предупреждение для проверки, не утверждение о повышении привилегий. Запись 1117 сама по себе не снимает обнаруженную угрозу Defender. Включение защиты 5000 закрывает предупреждение о её отключении 5001.

По умолчанию события с важностью Warning/Critical сохраняют открытую проблему до «Решено», кроме правил с таймаутом. Каждое повторение продлевает таймаут от последнего наблюдения; недоступное чтение приостанавливает автозакрытие. Несколько сообщений о той же аварийной загрузке объединяются в открытую проблему. История сохраняет отдельные записи. Плановая перезагрузка User32 1074 — информационная запись.

Сбор ограничен: очередь агента 128 событий, пакет до 32 и 80 тысяч символов сериализованных событий, история сервера 2000 записей на устройство, ключи дедупликации 8000. Заполненная очередь приостанавливает чтение, не удаляя ещё не переданные записи. Очистка/перезапись журнала обнаруживается по курсору и отражается в состоянии чтения. Если сама Windows уже перезаписала записи, восстановить их агент не сможет. Это оперативный мониторинг, не архив всех журналов и не SIEM.

Успешные входы 4624 запрашиваются только для до 16 недавно наблюдавшихся сетевых IP с ошибками 4625, чтобы не передавать все штатные входы. Проверка успеха после серии ошибок использует окно 10 минут. Пользовательские правила аудита требуют включённого аудита Windows; программа не включает его автоматически. Сообщение Windows ограничено 1000 символами, простые поля password/token/secret маскируются, но не считай это гарантией удаления всех секретов. Доступ к журналам давай только нужным пользователям.

Агент работает как LocalService с отдельным SID. Установщик назначает этому SID только маску чтения 1 в DACL разрешённых журналов; права записи/очистки и членство в администраторах не выдаются. При удалении снимается только собственная запись чтения. Ошибки назначения записываются в journal-access.txt. Отсутствующий журнал Defender считается неприменимым; недоступный Security не показывается как подтверждённо здоровый. Служба EventLog по-прежнему контролируется отдельно от содержимого журналов.

Обслуживание сохраняет историю и проблемы, подавляя уведомления. После обслуживания сохранившаяся проблема отправляется один раз. Новая критическая эскалация может отправить дополнительное уведомление. Уведомления идут в общий Telegram; настройка важности Telegram действует и здесь.

Чтение выполняется в отдельной задаче раз в сутки, при ошибке повтор через час; предыдущие успешные сведения сохраняются с прежней датой.

RouterOS: выбери stable или long-term в свойствах MikroTik → Мониторинг. Каталог опрашивается сервером раз в сутки; при ошибке повтор через час. Сравнивается только та же основная ветка 6/7, для beta/rc неизвестного формата показывается неизвестное состояние. Нет команды check-for-updates, установки, перезагрузки или изменений на устройстве. Официальные сведения версии могут быть недоступны — тогда зелёное подтверждение «обновлений нет» не выдумывается.

## Проверка после публикации на Windows

1. Запусти PUBLISH.bat; VERIFY.cmd должен завершить обе программы проверок до публикации.
2. Обнови сервер и клиент, затем один агент через пакет обновления. Убедись, что ключ и DeviceId не изменились.
3. Открой состояние чтения журналов, проверь journal-access.txt. Если чтение запрещено, исправь адресно политику/ACL, не повышая права службы.
4. Добавь тестовое правило для известного источника в Application, сгенерируй тестовую запись штатным администраторским средством Windows. Проверь запись, проблему, один Telegram и «Решено». Переотправка одного пакета не должна дублировать их.
5. Проверь отключение связи и восстановление очереди, обслуживание, недоступный журнал, новое событие после ручного закрытия. Дождись собственного штатного поиска Windows Update и сравни список / дату; не используй отсутствие значка как доказательство безопасности.

GUI, EventLogReader/ACL, COM WUA, служба и реальная доставка Telegram требуют проверки на Windows. Автотесты модели не заменяют эту проверку.
