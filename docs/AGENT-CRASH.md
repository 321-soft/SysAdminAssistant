# Служба Windows-агента: восстановление и диагностика

Начиная с 0.42.1 установщик и обновлятор настраивают действия Windows Service Control Manager: после первого сбоя — перезапуск через 15 секунд, после второго — через минуту, после последующих — через 5 минут. Счётчик сбрасывается после суток без сбоев. Обычная остановка службы не считается сбоем. Если агент обновился старым обновлятором, настройку применит новый обновлятор при ближайшем запуске его задачи.

Проверка настроек в PowerShell:

```powershell
sc.exe qfailure SysAdminAssistantAgent
sc.exe qfailureflag SysAdminAssistantAgent
```

Чтобы включить восстановление сразу, пока установлен старый агент, выполните от администратора:

```powershell
sc.exe failure SysAdminAssistantAgent reset= 86400 actions= restart/15000/restart/60000/restart/300000
sc.exe failureflag SysAdminAssistantAgent 1
```

Если служба уже остановлена, запустите её вручную: `Start-Service SysAdminAssistantAgent`.

## Какие данные отправить для разбора

- `C:\ProgramData\SysAdminAssistantAgent\crash.json` — последнее необработанное исключение агента версии 0.42.1 или новее.
- `crash.previous.json` в том же каталоге — предыдущее падение.
- При принудительном завершении процесса, нативной ошибке, сбое загрузки среды выполнения или невозможности записи файл может не появиться. Проверьте «Просмотр событий → Журналы Windows → Система» (Service Control Manager) и «Приложение» (.NET Runtime, Application Error, Windows Error Reporting). Ищите записи по времени сбоя и имени SysAdminAssistantAgent / SysAdminAssistant.Agent.exe.

Файлы падений содержат этап, версию, тип исключения, HRESULT и имена методов. Содержимое исключения, команды, адрес сервера, ключи и пароли не записываются. Не отправляйте bootstrap.json, identity.bin и весь каталог данных.

## Если обновление не смогло заменить DLL или EXE

В 0.42.4 установщик ждёт остановки службы и завершения её процесса, затем проверяет блокировки файлов до начала замены. Обновление не останавливает зависимые службы и не завершает посторонние процессы. При временном конфликте он ждёт освобождения файлов; при отказе восстанавливает только изменённые файлы. Если откат не удался, сохранённая копия остаётся в указанной папке Maintenance. Следующее автообновление не продолжает поверх незавершённой операции.

Если агент уже обновился и передаёт свежие отчёты, повторно переустанавливать его не нужно. Если старый обновлятор продолжает падать, новый код не сможет заменить его сам, пока старый обновлятор не завершит установку. Соберите сервер и клиент из одного выпуска, затем в карточке устройства выберите **«Пакет обновления агента»** и запустите подписанный установщик на нужном узле. Ключ и регистрация остаются. Если файлы всё ещё заняты, проверьте, не запущен ли дополнительный экземпляр агента вручную; для диагностики можно использовать DIAG_AGENT_PROCESSES.ps1. Не удаляйте каталог ProgramData и не отзывайте регистрацию ради ремонта.


## Если политика восстановления не появилась после обновления

До 0.42.7 проверка установленной службы искала раздел реестра по неверному пути. Это могло сорвать проверку на существующей установке до скачивания нового выпуска. В 0.42.7 установщик проверяет параметры, которые вернул Windows SCM, а автообновлятор повторно сверяет их при каждом запуске задачи и записывает только при отличиях. Для проверки используйте `sc.exe qfailure SysAdminAssistantAgent` и `sc.exe qfailureflag SysAdminAssistantAgent`.

Если на проблемном узле старый обновлятор не может скачать или применить исправление, создайте подписанный «Пакет обновления агента» с сервера и клиента одного выпуска и запустите на этом узле. Ключ и регистрация сохраняются. Проверяйте фактические параметры службы на Windows, начиная с одного некритичного узла.
