## Переход на 0.42.14

Сохраните резервную копию базы и каталога данных, затем обновите существующий сервер и клиент. При публикации через PUBLISH.bat включите установщики .NET или заранее положите проверенные файлы в RuntimePackages. Сервер и клиент используют комплектные установщики, если текущая версия среды ниже 10.0.14. Для сервера нужны Desktop Runtime и ASP.NET Core Runtime, для клиента — Desktop Runtime.

Работающий Windows-обновлятор сначала получает совместимую версию агента 0.42.14. При следующем запуске новый обновлятор скачает .NET Desktop Runtime 10.0.14 x64 с сервера Assistant, сверит подпись и хеши и установит его без автоматической перезагрузки. В последующих обновлениях с этим обновлятором проверка и установка среды идут до замены агента. Если требуется плановая перезагрузка, статус покажет это отдельно. Регистрация сохраняется. Если старая задача автообновления не запускается, используйте подписанный пакет обновления именно этого устройства.

KSC: обновите сервер и клиент из этого выпуска, затем откройте карточку KSC → «Подключение к KSC» → «Сертификат OpenAPI». Используйте «Копировать команду» на сервере KSC, вставьте полученный SHA-256 в поле и нажмите «Проверить подключение». После успеха примените настройки и включите фоновый сбор. При смене отпечатка прежнего подключения сохраняются позиция чтения и привязки устройств.

Linux-агент публикуется со встроенной .NET 10.0.14; для этого нужен новый подписанный выпуск агента с сервера. Патч системной среды сам по себе его не обновляет. Если версия не меняется, проверьте, что установлен сервер из полного комплекта PUBLISH.bat и Linux-агент продолжает отправлять отчёты. Linux загружает пакет отдельно от Windows и не использует поле Runtime. Статус в карточке агента описывает загрузку; применение уже скачанного пакета показывает журнал systemd:
```bash
sudo /opt/sysadminassistant-agent/agent --preflight
systemctl list-timers --all sysadminassistant-agent-update.timer --no-pager
sudo journalctl -u sysadminassistant-agent -u sysadminassistant-agent-update -n 60 --no-pager
```

Для действующей установки WebWatchdog обновите вместе `receiver.php` и `lib.php` из одного выпуска, оставив конфигурацию и каталог состояния на месте. Если receiver — короткий публичный файл, который подключает приватный receiver, обновите именно приватную копию. После замены проверьте, что сервер получает подтверждение очередного сигнала.

## Переход на 0.42.9

Обновите сервер и клиент из одного выпуска. В карточке Linux-агента доступна справка по его обновлению. Windows-пакет на Linux не используется. Linux-агент проверяет новый выпуск после успешной связи с сервером, а systemd применяет скачанный пакет. Проверка таймера и принудительное применение уже скачанного выпуска:

```bash
systemctl status sysadminassistant-agent-update.timer --no-pager
sudo journalctl -u sysadminassistant-agent-update.service -n 30 --no-pager
sudo systemctl start sysadminassistant-agent-update.service
```

Если служба пишет «Обновление не загружено», проверьте свежесть отчёта агента и наличие Linux-шаблона на обновлённом сервере. Команда запуска службы обновления не выполняет скачивание.

## Переход на 0.42.8

Сначала сохраните копии базы и конфигурации, затем обновите существующий сервер и клиент через соответствующие Setup.exe. Сервер 0.42.8 принимает запросы старых Linux-агентов: при включённом автообновлении переустановка и повторная регистрация не нужны. Новый Linux-агент отправляет подпись, привязанную к операции; его следует развёртывать после обновления сервера.

Убедитесь, что после обновления служба сервера запущена, а в карточке тестового Linux-узла отображаются новая версия и свежий отчёт. При занятой очереди раздачи агент повторит запрос позже. Если выпуск отклонён, проверьте `journalctl -u sysadminassistant-agent-update.service` и `/opt/sysadminassistant-agent/update-result.json`. Старые служебные пакеты очищаются новой версией; карантины, созданные вручную под другим именем, остаются на месте.

Если Windows-агент 0.42.3 показывает «Нет ожидаемой службы агента», выполните на наблюдаемом сервере `sc.exe query SysAdminAssistantAgent`. Если служба существует, после обновления сервера и клиента создайте **пакет обновления** именно этого устройства и запустите его от администратора. Оставьте автообновление включённым. Такой пакет обновляет и старый планировщик, не меняя регистрацию. Если Windows возвращает ошибку 1060, сохраните каталог данных агента и разберите, почему служба отсутствует, прежде чем что-либо удалять.

## Переход на 0.42.0 / 0.42.1

1. Сохраните резервную копию БД и каталога данных сервера. Для SQL используйте согласованную SQL-копию, а не копирование файлов MDF/LDF.
2. Соберите архив через PUBLISH.bat на Windows. Для двух установщиков выберите 1, для установщиков и папок — 3. Сохраните прежний ключ издателя; не удаляйте его при обновлении.
3. Запустите SysAdminAssistant_Server_Setup.exe и выберите обновление существующего сервера. Не запускайте REMOVE_SYSADMIN_SERVER_ALL.bat: он предназначен для полного удаления.
4. Обновите клиент из того же выпуска. При запросе закрытия сохраните открытые формы; принудительное завершение может потерять несохранённый ввод.
5. Проверьте запуск службы, вход клиента и свежие результаты фонового мониторинга. Агентов заново регистрировать не нужно: при разрешённых автообновлениях сервер выдаёт новые шаблоны.
6. Если KSC настраивался в предварительной сборке: включите роль в свойствах нужного устройства, затем явно привяжите прежнее подключение во вкладке Kaspersky. До привязки сбор приостановлен. История и позиция чтения сохраняются. Используется одно подключение KSC.

В этом выпуске добавляется поле роли KSC в таблицу устройств. Сначала обновляйте сервер, затем клиент; не сохраняйте устройства старым клиентом после перехода. Перед откатом сохраняйте актуальные данные и используйте согласованную резервную копию; замена файлов программы не восстанавливает SQL-базу.

## Существующая установка

Сделайте собственную резервную копию БД и конфигурации. Для перехода с прежнего сервера на выпуск с онлайн-обслуживанием один раз запустите новый серверный Setup.exe от администратора и выберите обновление существующей установки. Не используйте полную очистку и не создавайте новую регистрацию агентов. Обновите клиент его Setup.exe.

Серверный мастер сохраняет программу и локальные данные в резервную копию, останавливает и обновляет службу, проверяет запуск и HTTPS. При неудачном запуске выполняется возврат предыдущих файлов. Для SQL Server перед интерактивным обновлением требуется собственная резервная копия базы: копия каталога ProgramData не заменяет SQL BACKUP.

## Кнопка в клиенте

Откройте «Обновления» → «Проверить обновления». Само открытие окна не запускает установку. Клиент и сервер обновляются отдельными кнопками; сервер — только главным администратором, что проверяется сервером, а не только интерфейсом.

Источники release.json задаются в настройках сервера через клиент: основной HTTPS-адрес и необязательное зеркало. По умолчанию адрес — `https://assistant.321.su/releases/release.json`. Издатель должен разместить этот файл; наличие адреса в настройке не означает, что хостинг уже настроен.

Для публикации разместите два неизменённых Setup.exe по адресам из подписанного манифеста. Скопируйте release.json также в расположение источника обновлений. Зеркало GitHub может отдавать тот же манифест; адрес альтернативной загрузки каждого пакета должен быть включён при подписи через SAA_RELEASE_MIRROR_BASE_URL. Манифест действует 90 дней; продлевайте публикацию подписью, а не редактированием текста. Проверяются продукт, версия, совместимость, схема, срок, подпись, размер и SHA-256.

При обновлении клиента запускается защищённый помощник из Program Files с запросом UAC. Он повторно проверяет подписанный манифест и загружает Setup.exe в защищённый каталог; пользовательский каталог используется только для чтения заявки. Старый клиент закрывается перед заменой файлов. Установщик ожидает завершения процесса и проверяет новую программу до завершения; настройки пользователя и серверные данные сохраняются.

При обновлении сервера создаётся явная заявка. Локальная задача обслуживания под SYSTEM проверяет её примерно раз в минуту и устанавливает только подписанный разрешённый выпуск. Это не фоновая автоматическая установка новых версий. Перед заявкой для SQL Server выполняется COPY_ONLY BACKUP WITH CHECKSUM в штатный каталог резервных копий SQL; если нет прав или каталога, обновление не разрешается. Удалённая SQL-копия находится на машине SQL Server, а не обязательно на сервере Assistant.

Статус обслуживания: `C:\Program Files\SysAdmin Assistant Maintenance\status.json`. Программа обслуживания и её конфигурация защищены правами каталога Program Files. Заявка в каталоге данных не содержит произвольных команд или пути исполнения. Закрытие окна ожидания не отменяет установку. Не запускайте вторую установку, пока не проверено состояние первой.

При ошибке сохраните журнал установщика и путь резервной копии, проверьте службу SysAdminAssistantServer и HTTPS. Автоматический откат программы не равен восстановлению удалённой SQL-базы: SQL-восстановление после нарушения данных выполняет администратор из проверенной копии. Не удаляйте рабочую БД для снятия сообщения об ошибке. Если изменены условия соглашения, используйте интерактивный установщик.

## English

Back up the database and configuration first. Install the new server release once through GUI setup to register the protected maintenance task, preserving existing data and agent enrollment. Update the client with its setup. Do not use destructive cleanup for upgrades.

Use Updates → Check for updates, then explicitly choose the client or server action. Only the principal administrator can authorize a server update. The task runs periodically but never installs a new release without an authorized request. Agent automatic updates remain independent.

Configure the main HTTPS release.json feed and optional mirror through the client. Upload the exact generated installers and signed manifest to their declared locations. Signed package mirrors must be declared before publishing. Manifests expire after 90 days; editing the JSON invalidates the signature.

Online server updates require a successful SQL COPY_ONLY backup with CHECKSUM when SQL Server is used. The backup is written on the SQL host. Interactive upgrades require an administrator-managed SQL backup. File rollback does not restore a remote SQL database; database recovery remains an administrator operation. SQLite/local data and program backups are managed by setup.

Closing the waiting window does not cancel an active server transaction. Review the protected maintenance status, service and installer log before retrying. A changed EULA requires interactive setup. Preserve the publisher signing key and never publish it.

The installed client uses a protected, versioned helper for UAC-approved updates. The helper validates the signed request and downloads to protected staging before launching setup. A portable client must first be installed with Setup.exe to enable this path.


### Поведение подключений и счетов с 0.42.7

Сохранённый пароль нельзя перенести на новый адрес, порт, логин или новый отпечаток MikroTik. При правке этих параметров введите пароль в форме, включая проверку подключения. На первом запуске существующие индивидуальные подключения MikroTik привязываются к текущему адресу устройства. Старый общий пароль MikroTik используется только для адреса, явно сохранённого в общих настройках; для остальных устройств настройте отдельное подключение.

Фоновое распознавание вложений счёта выполняется только для отправителя из списка с успешной настроенной проверкой SPF/DKIM. Остальные вложения в PDF/OCR не передаются. Проверенные документы можно загружать вручную.

Клиент проверяет подписанный выпуск при открытии основного окна и каждые два часа. Зелёная точка рядом с «Обновлениями» означает, что доступна более новая версия. Скачивание и установка начинаются по вашей команде. При ручной установке запускайте новый Setup.exe из папки загрузок. Если клиент скрыт в трее и установщик просит завершить его, выберите «Выход» в меню значка.

Для перехода на 0.45.1 с предыдущей редакции лицензии запустите установщик соответствующего компонента и примите редакцию 1.1. Проверка обновлений продолжит показывать наличие выпуска.
